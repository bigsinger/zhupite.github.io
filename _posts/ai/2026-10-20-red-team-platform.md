# 开源 Benchmark 框架综合评估报告

结合你们的实际建设目标，我把前面讨论的 5 个项目放在同一套评估框架下比较：

- 题库管理：是否能维护、分类、版本化和审核 Benchmark Case。
- 考试执行：是否能组织批次、运行测试、自动判分、回归复测。
- 安全攻防：是否适合提示词注入、敏感数据泄露、越权工具调用和完整 Agent 攻击链。
- 多产品扩展：是否能接入人脸活体、移动应用加固等非 LLM 产品。
- 企业运营：是否能支持团队协作、权限隔离、隐藏题管理、审计和长期运营。
- 落地成本：直接复用多少、需要二次开发多少，以及是否会被特定平台绑定。

先明确一个评估口径：这里说的“支持”，分为三种——开源项目原生具备、通过代码或配置可实现、需要自建或依赖商业版。这三种不能混为一谈。

### 对你们最重要的一个区别

对于前三个专项——敏感数据检测、意图识别、提示词注入检测——大多数框架都能通过自定义数据和判分器实现离线评测。

但整体 Agent 攻击 Benchmark 不能只判断模型有没有说出正确答案。它需要验证：

- 工具是否真的执行了；
- 是否访问或外传了不允许的数据；
- 权限边界是否被突破；
- 攻击链在哪一步被拦截；
- 正常任务是否仍能完成。

这时，执行环境、轨迹采集和结果 Oracle 比题库本身更关键。Inspect AI 和 PyRIT 值得重点验证这部分能力；Promptfoo 则适合更快建立可重复的安全测试与回归流程。

| PyRIT      | 攻击研究和红队编排能力突出；适合多轮攻击、攻击技术组合、攻击结果采集                    | 不是通用 Benchmark 题库；正常任务评测、产品专业管理和企业题库治理不是其重点              | 通用 Case 层、非 LLM 执行器、考试批次、题库审核、综合成绩统计               | 红队攻击测试接入：约 1–3 人周；多产品管理平台：约 8–16 人周            |

工作量仅用于立项初估。若要做到生产级权限、审计、高可用和完整审批流程，实际投入可能明显增加；多个框架并行集成也会带来额外维护成本。

## 七、最终建议：先验证两条路线，不要一开始就全都集成

路线 A：Langfuse + 自建轻量运营层

优先验证题库管理

适合希望尽快得到可视化题库、版本管理、数据集实验和统一结果工作台的团队。重点验证 Hidden Set 隔离、Case 自定义字段，以及人脸活体和 App 加固结果能否接入。

路线 B：Promptfoo + 自建统一题库管理层

优先验证安全测试执行

适合先快速落地 Agent 安全攻防、提示词注入测试和回归考试。统一题库、审批、专业管理和 Hidden Set 权限由你们掌控，其他产品通过适配器接入。

我的建议是，用同一批 30–50 个 Agent 安全 Case，分别验证这两条路线，并加一个复杂攻击链场景和一个非 LLM 产品模拟接入任务。对比实际开发量、判分准确性、题库维护体验和权限边界，再决定架构。

最后提醒一点：不要让题库管理工具决定你们的 Benchmark 数据模型。 先确定统一 Case Schema、版本、分层、来源和判分规范，再让框架适配你们的标准。这样未来替换执行引擎或新增产品专业时，题库和历史成绩不会被某个开源项目锁死。
